# FileSearch 복원 프로젝트

기존 `FileSearch.exe`에서 복원한 Windows용 Python 프로젝트예요. `main.py`, `collector`, `common`, `searcher`의 원래 모듈 구성을 살렸어요. GitHub 접속 없이 폴더를 열어 코드를 수정하고 실행할 수 있어요.

## 실행

Python **3.13, Windows 64비트**, **PySide6 6.12.0**, **olefile 0.47**, **Pillow 13.0.0**을 사용해요. SQLite는 Python에 포함되어 있어 따로 설치하지 않아요. 원본은 CPython 3.13.0이었어요. Python이 없다면 [공식 배포 페이지](https://www.python.org/downloads/windows/)에서 설치해 주세요.

프로젝트 폴더에서 PowerShell을 열고 다음 명령을 실행해요.

```powershell
py -3.13 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe main.py
```

Python 실행 명령이 `python`이라면 첫 줄을 `python -m venv .venv`로 바꿀 수 있어요. 가상환경을 활성화하지 않고 실행하는 방식이라 PowerShell 실행 정책 변경은 필요하지 않아요.

처음 패키지를 설치할 때는 PyPI 연결이 필요해요. GitHub, 원본 EXE, 추출한 바이트코드는 앱 실행에 필요하지 않아요. 설치 후에는 `run.cmd`로도 실행할 수 있어요.

## EXE 다시 만들기

코드를 저장하고 프로젝트 루트의 **`build.bat`를 더블클릭**하면 현재 소스로 EXE를 다시 만들어요. 실행 중인 `dist/FileSearch/FileSearch.exe`는 먼저 닫아 주세요. 빌드가 끝나면 성공/실패 메시지를 확인할 수 있도록 창을 열어 둬요.

```powershell
.\build.bat
```

결과는 **`dist/FileSearch/FileSearch.exe`**예요. 이전 EXE에 소스 변경이 자동으로 반영되는 것은 아니며, 수정 후 배치파일을 다시 실행해야 해요. `run.cmd`는 빌드 없이 Python 소스를 바로 실행할 때 사용해요.

배치파일은 `.venv`를 사용하고, 없으면 프로젝트 내부 `.build-python` 또는 설치된 `py -3.13`으로 가상환경을 만들어요. 필요한 패키지를 `requirements-build.txt`에 맞춰 준비한 뒤 `FileSearch.spec`로 새로 빌드해요. 최초 설치나 패키지가 추가된 경우 인터넷 연결이 필요할 수 있어요. 자동 실행에서는 `build.bat --no-pause`로 마지막 대기를 생략할 수 있어요.

현재 PC에는 `E:\Projects\FileSearch\.build-python`에 Python 3.13.0을 준비했어요. `.venv`가 이 Python을 사용하므로 두 폴더를 유지해 주세요. 시스템 Python 설치나 PATH 변경 없이 빌드할 수 있어요. `.build-python`, `.venv`, `build`, `dist`는 Git에서 제외해요. 다른 PC에서 소스를 내려받으면 Python 3.13 64비트를 설치하거나 별도로 빌드 환경을 준비해야 해요.

빌드 설정은 DLL 검색 경로를 프로젝트 Python과 Windows 폴더로 한정해요. 다른 프로그램이 PATH에 추가한 동명의 ICU DLL 등이 실행파일에 섞이지 않도록 하기 위한 설정이에요.

수동으로 빌드할 때는 다음 명령도 사용할 수 있어요.

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-build.txt
.\.venv\Scripts\python.exe -m PyInstaller --noconfirm FileSearch.spec
```

결과는 `dist/FileSearch/FileSearch.exe`예요. 실행 파일과 옆의 `_internal` 폴더를 함께 배포해요. 원본 `.spec` 파일이 배포본에 없어서, 기존 배포 구조에 맞춰 새로 작성했어요. 새 EXE 자체의 해시가 이전 EXE와 같다는 뜻은 아니에요.

## 본문 검색 흐름

`MainWindow.run_search()`는 체크박스 값을 `SearchRequest`에 담아 작업 스레드를 시작하고, 완료된 `SearchResult`를 화면에 전달해요. 실제 분기는 `searcher/search_pipeline.py`의 `run()`에서 처리해요.

| 함수 | 역할과 반환값 |
| --- | --- |
| `run` | 파일명/본문/태그명 분기, 캐시 동기화, 결과 병합. 결과·실패 목록·캐시 처리 건수·취소 여부를 반환해요. |
| `read_file_metadata` | 하위 폴더의 전체 경로·파일명·수정 시각(ns)·크기를 읽고, 탐색 실패도 함께 반환해요. |
| `read_sqlite_metadata` | 현재 검색 폴더에 속한 캐시 메타데이터와 처리 상태만 읽어요. 본문은 읽지 않아요. |
| `compare_metadata` | 신규·수정·재시도·유지·삭제로 분류해요. DB를 변경하지 않아요. |
| `extract_file_body` | 형식별로 전체 본문을 추출해요. 실패나 취소를 빈 본문으로 바꾸지 않아요. |
| `sync_body_cache` | 신규·수정·실패 파일의 본문을 읽고 메타데이터와 함께 저장해요. 사라진 파일의 캐시도 정리해요. |
| `search_keyword_body` | 정상 캐시를 한 파일씩 읽고, 문구가 포함된 파일 목록과 본문 발췌를 반환해요. |
| `search_keyword_tag` | SQLite의 태그명에서 문구를 찾아, 후보 파일의 중복 없는 결과 목록을 반환해요. |

본문 캐시는 `%APPDATA%\FileSearch\body_cache.sqlite3`에 저장해요. 검색 루트와 전체 파일 경로를 식별자로 쓰므로 하위 폴더에 이름이 같은 파일도 구분해요. 본문 전문을 TEXT로 저장하며 FTS/단어 색인은 만들지 않아요. EXE를 빌드하면 SQLite와 HWP 읽기 모듈도 함께 포함해요.

- 첫 본문 검색에서는 선택한 종류·날짜 조건에 해당하는 지원 파일을 읽어요. 이후에는 수정 시각과 크기가 같은 정상 캐시를 재사용해요. 원본 본문 대신 캐시 본문을 매번 순회하는 방식이에요.
- 메타데이터 탐색은 필터와 무관하게 전체 하위 폴더를 확인해요. 필터 때문에 결과에서 빠진 파일을 삭제된 것으로 판정하지 않아요. 심볼릭 링크와 Windows 정션은 따라가지 않아요.
- 폴더 접근이나 파일 상태 확인에 실패하면 그 검색에서는 삭제 정리를 보류해요. 다른 검색 루트의 캐시는 삭제하지 않아요.
- 본문을 읽기 전후에 파일 상태를 다시 확인해요. 중간에 바뀌었거나 추출에 실패하면 이전 본문을 검색 결과에 쓰지 않고, 다음 검색에서 다시 시도해요. 실제 빈 문서는 정상 캐시로 저장해요.
- 검색 취소 시 이미 저장한 캐시는 유지하고, 불완전한 검색 결과는 화면에 표시하지 않아요. 진행 창에서 취소할 수 있고 오류 상세는 결과 상태 문구에 마우스를 올리면 보여요.
- 수정 시각과 크기를 모두 원래대로 유지한 내용 변경은 감지하지 못해요. 파일 이름 변경·이동은 기존 경로 삭제와 새 경로 추가로 처리해요.

## 검색 규칙과 지원 범위

- **파일명만**: 기존처럼 띄어쓰기로 나눈 단어가 파일명에 모두 있는지 확인해요.
- **파일 내용만**: Ctrl+F처럼 입력 전체의 부분 문자열을 찾아요. `계약금`은 `선급계약금을`에서도 찾아요. 대소문자는 구분하지 않고 한글 자모 표현은 NFC로 통일해요.
- 본문의 공백·탭·문단 구분은 보존해요. `계약금을 지불한다`는 연속된 그 문구를 찾으며, 중간에 다른 단어나 줄바꿈이 있으면 일치하지 않아요. `%`, `_`, `*`, 따옴표는 일반 글자예요.
- **태그명만**: 입력한 문구가 태그명에 포함된 파일을 찾아요. 앞뒤 공백·대소문자·한글 자모 차이는 무시하며 중간 공백은 그대로 비교해요.
- **여러 항목 선택**: 파일명·본문·태그명 중 선택한 항목 하나라도 일치하면 표시하고, 경로 기준으로 중복을 제거해요. 본문도 일치하면 본문 발췌를 유지해요.
- 검색어가 비어 있으면 이름 검색은 필터에 맞는 전체 파일, 본문 검색은 정상적으로 읽은 지원 파일, 태그명 검색은 태그가 붙은 파일을 보여 줘요.
- **HWP 5.x**: BodyText의 모든 문단 레코드를 읽어요. 표·글상자·각주 등의 텍스트도 포함해요. `PrvText` 미리보기만 읽는 방식은 아니에요. 암호·배포용·이전 HWP 형식은 지원하지 않아요.
- **HWPX**: ZIP 내부 본문 구역의 문단·텍스트 런을 순서대로 읽어요. 레이아웃을 재현하는 기능은 아니에요.
- **TXT**: UTF-8(BOM 포함), BOM이 있는 UTF-16, CP949를 지원해요.
- PDF·Word·Excel·PowerPoint는 파일명·태그명 검색이 가능하고, 본문 검색에서는 미지원 건수로 안내해요. 독립 이미지 파일의 OCR은 지원해요.
- HWP/HWPX 안에 삽입된 이미지와 임베디드 첨부 파일의 내용은 추출하지 않아요. 독립 이미지 파일은 아래 OCR 방식으로 읽어요. 처리 한도는 구역/텍스트 데이터 64 MiB, 문서 본문 약 3,355만 글자이며 초과 파일은 실패로 안내해요.

이번 변경은 코어 회귀 검사 40개(기존 17개 포함), 기존 GUI 검사 23개, 본문 GUI 검사 18개를 통과했어요. 본문 GUI 검사는 실제 작업 스레드의 검색·미리보기·캐시 재사용·취소 후 재시도를 포함해요. 공개 [pyhwp 시험 문서](https://github.com/mete0r/pyhwp/tree/master/tests/hwp5_tests/fixtures) 8개도 별도로 확인했으며, 일반 문서 6개를 추출하고 암호·배포용 문서 2개는 해당 사유로 제외했어요. 공개 샘플 파일은 프로젝트에 포함하지 않았어요.

본문 검색 추가 시 `build.bat`로 Windows EXE를 생성했고, 당시 앱 모듈 23개의 코드가 소스와 일치하는지 확인했어요. `_sqlite3.pyd`, `sqlite3.dll`, `olefile` 및 새 검색 모듈도 포함해요. EXE는 별도 테스트 설정의 화면 없는 Qt 모드로 직접 실행하여 Qt와 SQLite 초기화 및 시작 오류가 없음을 확인했어요. 검색·미리보기·취소의 상세 동작은 Python 소스 GUI 검사로 검증했어요.

## 현재 기능 상태

- 기본 저장 위치는 `D:\모은파일`이에요. 파일 모으기 창에서 변경할 수 있어요.
- 설정은 `%APPDATA%\FileSearch\settings.json`에 저장해요.
- 파일명 검색과 SQLite 캐시를 사용하는 본문 검색을 연결했어요. 본문 검색을 켜면 문구 검색 안내와 지원 형식을 표시해요.
- 태그 부착·선택 제거·전체 태그 관리와 실제 부착 수 표시를 연결했어요. 왼쪽 태그 더블클릭으로 문서를 바로 볼 수 있어요. 검색창의 태그명 입력 검색도 사용할 수 있어요. 최근 추가·중복 파일 메뉴는 아직 구현하지 않았어요.
- 본문 검색으로 찾은 파일을 선택하면 일치한 문구 주변을 보여 줘요. 검색 결과는 기존처럼 처음 500개만 표시해요.
- 원본의 복사·이동·중단 복구 로직을 그대로 보존했어요. 복구 로직에서 확인한 기존 제약은 복원 기록에 적었어요.

원래 주석·공백·작성 이력까지 되살린 것은 아니에요. 남아 있던 docstring, 한글 문구와 스타일 문자열은 보존했어요. README, 테스트, `pyproject.toml`, 패키지 목록, 빌드 설정은 복원 후 작업을 이어갈 수 있도록 새로 추가했어요.

## 태그 사용법과 저장 구조

1. 검색 결과 왼쪽의 체크박스로 태그를 붙일 파일을 선택해요. 행을 눌러 미리보기만 여는 동작과는 별개예요.
2. 하단에 태그 이름을 입력한 뒤 **태그 부착**을 눌러요. 여러 개는 `계약서, 중요`처럼 쉼표로 구분해요. 이미 있는 이름은 기존 태그를 재사용하고 없는 이름만 새로 만들어요. 하단의 기존 태그 체크 목록은 제거했어요.
3. **태그 제거**를 누르면 선택한 파일에 붙어 있는 태그가 표시돼요. 제거할 태그만 체크한 뒤 **선택한 태그 제거**를 눌러요. 다른 파일에 붙은 태그와 태그 이름 자체는 남아요.
4. 왼쪽 **+** 또는 **태그 관리**에서는 파일 선택 없이 태그를 만들 수 있어요. **태그 자체 삭제**는 확인 후 모든 파일에서 그 태그를 삭제해요.

결과 목록의 태그 열·미리보기·사이드바 개수는 저장 직후 갱신해요. 사이드바 숫자는 현재 검색 결과만이 아닌, 전체 폴더에 등록된 파일 경로 수예요. 태그 이름은 앞뒤 공백을 제거하고 한글 표현과 대소문자를 통일해 중복을 막아요. 이름은 64자까지, 쉼표와 제어 문자는 제외해요. 태그와 파일의 동일한 연결은 중복 저장하지 않아요. 파일 부착 작업은 한 트랜잭션으로 저장하므로 도중에 실패하면 해당 작업 전체를 되돌려요.

본문 캐시와 같은 `%APPDATA%\FileSearch\body_cache.sqlite3` 안에 다음 테이블을 사용해요. SQLite 별도 설치나 추가 Python 패키지는 필요하지 않아요.

| 테이블 | 저장 내용 |
| --- | --- |
| `tags` | 태그 ID, 표시 이름, 중복 확인용 이름, 사용자 지정 색 |
| `file_tags` | 파일 전체 경로와 태그 ID의 연결 |
| `tracked_files` | 이미 확인한 파일의 전체 경로와 파일명 |
| `body_cache` | 기존 본문·파일 메타데이터 캐시 |

`tagger/storage.py`의 `create_tag`는 태그 생성/재사용, `delete_tag`는 태그 자체 삭제, `show_tag`는 화면에 표시할 태그 목록과 파일 수 반환을 담당해요. `edit_tag`는 선택한 파일의 태그 이름을 변경하고, `attach_tags`와 `detach_tags`는 선택한 파일에 부착/제거하고, `read_file_tags`는 경로별 태그를 조회해요. 화면 출력은 `widgets.py`, `dialogs.py`에서 처리해 DB 함수가 GUI에 종속되지 않게 했어요.

태그는 본문 캐시 행에 종속되지 않으므로 본문을 다시 추출하거나 사라진 파일의 본문 캐시를 정리해도 유지돼요. PDF 등 본문 미지원 파일에도 붙일 수 있어요. **DB 파일 자체를 삭제하면 태그도 없어지므로 이 파일을 함께 백업해야 해요.**

현재 파일 식별자는 전체 경로예요. 파일을 수정해도 같은 경로면 태그가 유지돼요. 다른 경로에 같은 이름의 파일이 새로 발견되면 아래 확인 창을 통해 태그를 옮길 수 있어요. 파일명 자체가 바뀐 경우는 추적하지 않아요. 사라진 경로의 태그는 사용자가 정리하기 전까지 보존하고, 같은 경로에 파일이 다시 생기면 그 태그가 다시 표시돼요. 원본 파일 안에 태그를 기록하는 기능은 아니에요.

태그 기능 추가 후 코어 검사 **52개**, 기존 GUI **23개**, 본문 GUI **18개**, 태그 GUI **35개 항목**을 통과했어요. 태그 검사는 다중 부착·중복 방지·선택 파일에서만 제거·취소·전체 삭제·오류 시 입력 보존·재실행 후 보존·본문 캐시와의 공존을 확인해요. 새 EXE에 포함된 앱 모듈 **28개**의 코드가 현재 소스와 일치하고, 별도 테스트 프로필에서 Qt·SQLite 로딩과 태그 테이블 초기화를 확인했어요. 상세 버튼 동작은 Python 소스 GUI 검사로 검증했어요.

## 외부에서 이동한 파일의 태그 확인

검색할 때 현재 검색 폴더와 하위 폴더 전체의 경로·파일명을 대조해요. 본문 검색을 꺼도 실행하며, 검색어·파일 종류·날짜 조건에 맞지 않는 파일도 이동 후보 확인에 포함해요. 이미 읽은 파일 목록을 활용하고, 파일 해시나 Windows 파일 ID는 읽지 않아요.

태그가 붙은 기존 경로는 사라지고 같은 파일명이 **처음 보는 다른 경로**에서 발견되면, 검색 결과를 표시한 뒤 별도 **파일 경로 변경 확인** 창을 열어요. 이미 등록된 별개의 동명 파일은 후보에서 제외해요. 파일 이름은 확장자까지 비교하고 Windows의 경로 대소문자 차이는 통일해요. 프로그램이 이전에 보지 못한 파일은 실제 이동 파일인지 확정할 수 없으므로 사용자가 확인해요.

- 왼쪽에는 DB의 이전 경로, 오른쪽에는 새로 발견한 경로를 표시해요. 행을 더블클릭하면 **새 경로의 파일**을 연결된 프로그램으로 열어요.
- **선택한 태그 옮기기**: 체크한 연결만 승인해요. 기존 태그를 새 경로로 옮기고 이전 경로의 DB 메타데이터와 본문 캐시를 정리해요. 새 파일의 본문 캐시는 별도로 읽은 값을 사용하며 이전 본문을 복사하지 않아요.
- **선택한 이전 기록 삭제**: 태그 이동을 거절해요. 선택한 이전 경로의 태그 연결·경로 메타데이터·본문 캐시만 삭제해요. 실제 파일, 새 경로의 기록, 태그 이름 자체와 다른 파일의 태그는 유지해요.
- **나중에 확인**, 닫기, Esc: 변경 없이 보류해요. 체크하지 않은 항목도 보류하며, 조건이 계속 맞으면 다음 검색 때 다시 보여 줘요. 앱을 재실행해도 다시 확인할 수 있어요.
- 같은 이름의 후보가 여러 개면 후보별로 행을 보여 줘요. 승인할 때는 기존 파일 하나와 새 파일 하나를 일대일로 선택해야 해요.

폴더 탐색에 실패한 경우에는 이동을 판단하지 않아요. 적용 직전에도 기존 파일이 다시 생겼는지, 새 파일에 접근할 수 있는지, DB의 태그가 바뀌었는지 확인해요. 적용은 한 트랜잭션으로 처리하며 오류가 나면 해당 작업 전체를 되돌려요. 이전 버전의 태그·본문 DB는 유지하면서 경로 목록 테이블만 추가해요.

경로 변경 확인 추가 후 코어 검사 **69개**, GUI 검사 **102개 항목**(기존 23·본문 18·태그 35·경로 확인 26)을 통과했어요. 승인·거절·보류 후 재실행, 동명 후보 선택, 기존 경로 재등장, DB 오류 시 원상복구를 확인했어요. 재빌드 EXE의 앱 모듈 **30개**가 현재 소스와 일치하며 별도 테스트 프로필에서 Qt·SQLite와 경로 목록 테이블 초기화를 확인했어요. 상세 창 조작은 Python 소스 GUI 검사로 검증했어요.

## 태그 색과 바로 조회

- 태그는 옅은 배경색의 작은 표시로 보여요. 기본 색은 **빨간색**이며 기존 DB에 색 정보가 없으면 빨간색을 추가해요. 기존 태그 ID와 파일 연결은 유지해요.
- 왼쪽 **내 태그**의 태그를 **우클릭 → 색 변경**하면 색 선택 창이 열려요. 기본 색상표, 색상 영역, RGB/HTML 색 입력을 사용할 수 있어요. 확인하면 SQLite에 저장하고 사이드바·검색 결과·미리보기를 바로 갱신해요. 취소하면 바꾸지 않아요.
- 왼쪽 태그를 **더블클릭**하면 검색 버튼 없이 해당 태그가 붙은 문서를 보여 줘요. 현재 검색어·체크박스·종류·날짜 조건과 별개로, **DB에 등록된 모든 폴더**의 해당 태그 파일을 조회해요. 연결된 경로의 파일 상태만 확인하며 폴더 전체나 본문을 다시 읽지 않아요.
- 결과 제목에 보고 있는 태그를 표시해요. 일반 검색을 실행하면 태그 보기가 해제돼요. 태그 보기 중 태그를 떼거나 삭제하면 결과도 갱신해요.
- 사라졌거나 접근할 수 없는 파일은 표시하지 않고 상태 문구로 안내해요. 이 조회만으로 태그나 경로 기록을 지우지는 않아요. 경로 변경 확인은 기존처럼 일반 검색의 폴더 탐색에서 처리해요.
- 결과는 기존과 같이 처음 500개까지 표시해요. 태그 열에 공간이 부족하면 `+개수`로 표시하고 전체 태그는 미리보기와 도움말에서 확인할 수 있어요.

태그 색·바로 조회 추가 후 코어 검사 **76개**, GUI 검사 **134개 항목**(기존 23·본문 18·태그 35·경로 확인 26·태그 색/조회 32)을 통과했어요. 기존 DB 색 컬럼 추가, 색 저장·취소·재실행, 실제 더블클릭과 우클릭 메뉴, 태그 조회의 검색 조건 독립성, 태그 제거 후 결과 갱신을 확인했어요. 재빌드 EXE의 앱 모듈 **33개**가 현재 소스와 일치하며 한국어 Qt 번역이 포함돼요. 별도 테스트 프로필에서 EXE 실행·Qt/SQLite 로딩·기본 빨간색 DB 초기화를 확인했고, 상세 화면 조작은 Python 소스 GUI 검사로 검증했어요.

## 파일 유형 아이콘

검색 결과·미리보기·파일 모으기의 유형 선택에서 Windows에 등록된 파일 연결 아이콘을 우선 표시해요. 따라서 PDF 뷰어, 텍스트 편집기, Office 등 **PC의 파일 연결 설정에 따라 모양이 달라져요**. 연결 프로그램 설정은 변경하지 않아요.

- 아이콘이 없거나 Windows 조회가 실패하면 앱에 내장한 문서 아이콘을 표시해요. 한글·Word·Excel·PowerPoint·PDF·TXT·이미지 파일은 유형별 색과 표시를 사용하고 알 수 없는 형식은 일반 문서 모양이에요.
- 내장 아이콘은 Python 코드로 그리므로 외부 이미지 파일이나 추가 설치가 필요 없고 EXE에도 포함돼요.
- Windows 조회는 별도 작업 스레드에서 수행하고 확장자별로 한 번 불러와 재사용해요. 조회 중에는 내장 아이콘을 먼저 보여 줘요. 실제 파일이나 본문을 열어 아이콘을 추출하지 않아요.
- 실행 중 파일 연결 프로그램을 변경했다면 앱을 재실행해 새 아이콘을 불러와요.

Windows 조회는 [SHGetFileInfoW](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-shgetfileinfow)의 `SHGFI_USEFILEATTRIBUTES`를 사용해요. COM을 작업 스레드에서 초기화하고 사용한 아이콘 핸들을 해제해요.

아이콘 변경 후 코어 검사 **76개**, 기존 검색/수집 GUI **23개**, 태그 색/조회 GUI **32개**, 아이콘 전용 GUI **29개 항목**을 통과했어요. Windows 실제 아이콘과 내장 대체 표시, 조회 실패, 500회 요청의 캐시 재사용, 늦게 도착한 결과가 다른 파일의 미리보기를 덮어쓰지 않는지, 종료 시 작업 정리를 확인했어요. 새 EXE에 앱 모듈 **34개**가 현재 소스와 일치하고 배포 파일 **172개**의 복사 해시가 일치해요. 격리 프로필에서 EXE 실행도 확인했어요.

`build.bat`는 같은 경로의 `dist/FileSearch/FileSearch.exe`가 실행 중이면 **기존 배포 파일을 정리하기 전에** 빌드를 중단해요. 앱을 닫고 다시 실행하면 돼요. 실행 중 중단/파일 보존과 앱 종료 후 빌드 허용을 검증했어요.

파일 아이콘의 표시 검사를 보완했어요. 이미지 로딩에 성공해도 완전히 투명하거나 흰 배경에서 거의 보이지 않으면 내장 문서 아이콘을 유지해요. 화면에 보이는 크기에서 투명도까지 반영해 검사하며, 정상적인 Windows 아이콘은 그대로 사용해요. 아이콘 GUI **47개 항목**으로 투명·흰색·희미한 이미지와 실제 PC의 Word/Excel/PowerPoint 연결 아이콘을 검증했고, 검색 결과와 파일 유형 선택 화면을 캡처해 표시를 확인했어요.

## 검색창의 태그명 검색

**태그명** 체크박스를 켜고 검색 버튼을 누르면 `SearchRequest.tag_enabled`를 받아 `run()`에서 `tagger/search.py`의 `search_keyword_tag()`를 호출해요. `tags`와 `file_tags`를 연결해 태그명에 입력 문구가 포함됐는지 SQLite에서 확인해요. 예를 들어 `계약`은 `계약서`와 `선급계약금` 태그를 모두 찾아요. `%`, `_`, `*`, 따옴표는 일반 문자이며 SQL 매개변수로 전달해요.

일반 검색이므로 **현재 저장 폴더와 하위 폴더**, 파일 종류, 수정일 조건을 적용해요. 공통 폴더 탐색에서 읽은 메타데이터를 재사용해 결과를 만들고, 태그명만 켰을 때에는 파일 본문이나 본문 캐시를 읽지 않아요. 태그가 여러 개 일치해도 파일당 한 번만 표시하고, 파일명·본문 결과와도 중복을 제거해요. 후보 경로가 많으면 나눠 조회하며 검색 취소도 처리해요.

왼쪽 태그 더블클릭은 기존처럼 **그 태그 하나에 연결된 모든 등록 폴더의 파일**을 바로 보여 줘요. 검색창의 태그명 검색은 일부 이름으로 여러 태그를 찾으며 현재 폴더·검색 필터를 적용한다는 차이가 있어요.

태그명 분기 추가 후 코어 **88개**, 관련 GUI **77개 항목**(태그명 27·본문 18·태그 색/바로 조회 32)을 통과했어요. 검색 항목의 7가지 조합, 본문 미열람, 태그 중복·문자열 부분 검색, 필터·범위, 605개 후보 분할 조회, 취소, DB 오류와 재시도를 확인했어요.

## 선택한 파일의 태그 이름 수정

왼쪽 **내 태그 → 태그 우클릭 → 태그 수정**에서 새 이름을 입력하고 변경할 파일을 체크해요. 목록에는 현재 검색 결과와 별개로 **해당 태그가 붙은 모든 등록 경로**를 보여 줘요. 파일명이 같아도 전체 경로로 구분하고, **전체 선택 / 선택 해제** 버튼으로 한꺼번에 체크하거나 해제할 수 있어요. 파일명이나 경로를 더블클릭하면 문서를 열어요.

- **일부 파일 선택**: 선택한 파일의 해당 태그만 새 이름으로 바꾸고 기존 색을 이어받아요. 선택하지 않은 파일의 태그 이름과 각 파일의 다른 태그는 유지해요.
- **전체 선택**: 새 이름이면 기존 태그의 ID·색을 유지하며 이름을 변경해요.
- **이미 있는 태그 이름 입력**: 선택한 파일을 그 태그에 연결하고 그 태그의 색을 사용해요. 중복 연결은 만들지 않아요. 모든 파일을 옮기면 빈 기존 태그도 정리해요.
- **빈 태그**: 파일 선택 없이 이름만 수정할 수 있어요. 대소문자만 바꾸는 경우는 동일한 태그로 취급하므로 전체 파일을 선택해야 해요.
- **저장 실패·취소**: 취소는 변경을 저장하지 않아요. 저장 실패 시 입력과 선택을 유지해요. 수정 중 다른 창에서 선택한 연결이나 원래 태그 이름을 바꾼 경우에는 다시 확인하도록 안내해요.

이름 수정은 SQLite 트랜잭션 하나로 저장하며 파일 자체·본문 캐시·경로 메타데이터를 바꾸지 않아요. 태그 바로 보기 중 수정하면 해당 목록과 제목을 갱신하고, 기존 태그로 전부 합친 경우 그 태그의 결과를 보여 줘요. 일반 검색 결과의 태그 표시도 즉시 갱신해요. 등록된 경로의 실제 파일이 사라져 있어도 태그 정보는 수정할 수 있어요.

태그 이름 수정 추가 후 코어 **103개**, 관련 GUI **112개 항목**(이름 수정 45·색/바로 조회 32·기존 태그 35)을 통과했어요. 부분 수정·전체 이름 변경·기존 태그로 합치기·다른 태그 및 색 보존·취소·DB 오류 시 원상복구·재실행 후 보존을 확인해요. 상세 화면 동작은 Python 소스의 Qt GUI 검사로 검증해요.

이번 실행파일은 build.bat로 다시 만들었고, 앱 모듈 **35개**의 코드가 현재 소스와 일치해요. 격리 프로필에서 EXE 시작과 SQLite 태그 테이블 초기화도 확인했어요.

## 이미지 글자 검색 (내장 OCR)

**파일 내용**을 체크하고 검색하면 이미지 안에 적힌 한국어·영어도 찾아요. 파일 종류를 **이미지**로 선택하면 이미지 파일만 검색해요. 결과를 선택하면 기존 **일치한 본문 일부** 영역에서 OCR로 추출한 글자를 확인할 수 있어요.

- 지원 형식: PNG, JPG/JPEG, BMP, TIF/TIFF, 정지 WebP. TIFF는 모든 페이지를 순서대로 읽어요.
- OCR은 새로 발견한 파일이나 크기·수정일이 달라진 파일에만 실행해요. 추출 결과는 기존 SQLite의 body_cache에 전체 본문으로 저장하고 이후 검색에서 재사용해요. 정상적으로 읽었으나 글자가 없는 이미지도 빈 본문으로 저장하므로 매번 OCR을 반복하지 않아요.
- 오류나 취소로 완료하지 못한 파일은 다음 검색에 재시도해요. 이미지가 바뀐 뒤 읽기에 실패하면 이전 글자가 결과에 섞이지 않도록 해당 캐시를 무효화해요. 파일명·태그명 검색만 켠 경우에는 OCR을 실행하지 않아요.
- 사진의 EXIF 회전을 적용하고 투명 배경은 흰색으로 합성한 뒤 글자를 읽어요. 원본 이미지 파일은 바꾸지 않아요.
- OCR은 검색 작업 스레드에서 로컬 자식 프로세스로 실행해요. 진행 창에 **이미지 글자 인식 중**을 표시하며 취소하면 OCR 프로세스도 종료해요. 명령 창을 따로 띄우지 않아요.
- 손글씨, 흐린 사진, 여러 단이나 복잡한 배치, 세로·기울어진 글자는 오인식/누락이 생길 수 있어요. 추출 결과의 띄어쓰기와 줄바꿈에도 영향을 받으며 원본과 완전히 동일한 문자열을 보장하지 않아요.
- 처리 한도: 파일 64 MiB, 한 페이지 4,000만 화소, TIFF 100페이지, 파일당 인식 120초, 추출 글자 약 419만 자. 움직이는 WebP와 GIF, HEIC, 스캔 PDF 및 문서에 삽입된 이미지는 이번 지원 범위에 포함하지 않아요.

엔진은 [Tesseract 5.5.3 Windows 배포본](https://github.com/tesseract-ocr/tesseract/releases/tag/5.5.3)이고, 공식 [tessdata_fast](https://github.com/tesseract-ocr/tessdata_fast)의 한국어·영어 모델을 고정 커밋으로 포함해요. 엔진·모델·필수 DLL은 약 **52 MiB**예요. 사용자는 Tesseract나 Python을 따로 설치할 필요가 없고, OCR 중 인터넷 연결이나 외부 AI API도 사용하지 않아요.

빌드할 때 vendor/tesseract의 해시 목록을 검사하고 배포 폴더의 _internal/ocr_runtime에 그대로 복사해요. 원본 다운로드 주소와 SHA-256은 manifest.json, 구성요소의 라이선스와 소스 출처는 THIRD_PARTY_NOTICES.txt와 licenses 폴더에 있어요. **배포할 때는 EXE와 _internal을 포함한 dist/FileSearch 폴더 전체를 전달해요.** 소스로 실행할 때도 vendor/tesseract 폴더를 함께 유지해요.

OCR 추가 후 코어 **117개**, 관련 GUI **38개 항목**(OCR 20·기존 본문 18)을 통과했어요. 실제 한국어·영어 인식, 지원 이미지 형식, 투명 배경·회전·다중 페이지, 캐시 재사용·수정 파일만 재처리, 오류 후 복구, 취소·시간 초과 시 자식 프로세스 종료, 기존 문서 캐시·태그 보존을 확인했어요. 상세 화면 동작은 Python 소스의 Qt GUI 검사로 검증해요.

OCR 배포본의 앱 모듈 **37개**가 현재 소스와 일치하고 OCR 구성 파일 **86개**의 해시를 확인했어요. 번들에서 추출한 OCR 코드와 포함된 엔진으로 한국어·영어 인식, 한글·공백 설치 경로, 시스템 OCR 경로 없이 실행, SQLite 캐시 재사용과 수정 파일만 재처리를 검증했어요. EXE 시작은 격리된 화면 없는 프로필에서 별도로 확인했어요. 전체 배포 폴더는 **297개 파일, 약 222 MiB**예요.
